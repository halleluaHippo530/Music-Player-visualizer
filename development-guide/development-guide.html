v5.5.0 - DUAL-rAF ELIMINATED: Jungle Integrated into Main Loop (PERMANENT Slow-Motion Fix)
2026-08-09
  • ROOT CAUSE FOUND AND ELIMINATED — dual-rAF architecture removed: The jungle visualizer had its own independent requestAnimationFrame loop (the _loop() function with a fixed-timestep accumulator), separate from the main player's P._loop(). This dual-rAF architecture was the TRUE root cause of the persistent "blinking slow-motion" bug that occurred after repeated play/pause cycles. The dual-rAF caused: (1) Double CPU load — two loops competing for frame time, each doing its own work; (2) Accumulator death spiral — when FPS dropped, the accumulator required more steps per frame, which lowered FPS further, requiring even more steps; (3) State desync — the jungle's advance() read P.freqData and P.isPlaying at different times than the main loop wrote them, causing inconsistent audio coupling; (4) Resource accumulation — repeated start/stop cycles of the jungle's rAF loop leaked resources over time.
  • JUNGLE.tick(dt) — integrated rendering, exactly like cityscape: The jungle no longer has its own rAF loop. Instead, P._loop() calls JUNGLE.tick(dt) every frame when the jungle is visible — exactly like how cityscape rendering works. tick(dt) calls advance(dt) + render() in one step, using the SAME dt as cityscape (clamped to [0.25, 3.0] by P._loop). JUNGLE.start() and JUNGLE.stop() now just set/clear a _running flag — no rAF is scheduled. This is a minimal, surgical change: the 8000+ lines of jungle rendering code (drawSky, drawMountains, drawRiver, etc.) are unchanged. Only the loop architecture was rewritten.
  • Accumulator removed — simple dt-based timing like cityscape: The fixed-timestep accumulator (_accumulator, _FIXED_DT, _MAX_STEPS) is completely removed. The jungle now uses the same simple dt-based timing as cityscape: advance(dt) is called once per frame with the actual frame dt. At 60 FPS, dt=1.0 (same as before). At 30 FPS, dt=2.0 (one step instead of two). At 20 FPS, dt=3.0 (clamped, one step instead of three). Below 20 FPS, the simulation slows slightly but NEVER death-spirals — exactly like cityscape. No accumulator buildup, no excess draining, no step counting.
  • Dead variables cleaned up: Removed _rafId and _lastFrameT from the JUNGLE module — they were only used by the old independent rAF loop and are no longer needed. The tick function was added to JUNGLE's public API return statement.
  • Alpha management updated: When jungleOnly is true (jungle fully covers the screen), JUNGLE.setAlpha(1) is now called directly from the integrated rendering path in P._loop(), ensuring the jungle canvas opacity is always correct even when P.render() is skipped.

v5.4.0 - Jungle Slow-Motion Root Cause Fix + Temple/Theme Selection
2026-08-10
  • Root cause of jungle slow-motion identified and fixed: The jungle hsl() color cache used a plain JavaScript object with delete operations for eviction. After ~6000 entries were added and deleted, V8 transitioned the object to "dictionary mode" (slow property access), causing progressive slowdown. Property lookups became O(n) hash-table scans instead of O(1) inline offsets. This only affected the jungle because it has its own hsl() function with a separate cache — city/galaxy use the global hsl() which has a different cache
  • Map-based hsl cache: Replaced the plain object cache with Map, which is designed for frequent add/delete operations and maintains O(1) lookup regardless of operation history. Eviction uses Map.keys() iterator instead of Object.keys() (which creates a full array copy)
  • dt cap raised from 3.0 to 5.0: The previous cap caused slow-motion when FPS dropped below 20 — the simulation lost real time because dt was clamped. At 5.0, the simulation stays accurate down to 12fps. The death-spiral risk is mitigated by the staggered layer refresh system and the Map-based cache
  • Per-frame Path2D allocations eliminated: Rain rendering and lightning bolts used new Path2D() every frame, creating GC pressure. Replaced with ctx.beginPath() + ctx.rect() + ctx.fill() which achieves the same batching without allocation
  • Per-frame closure eliminated: drawPantherChase() created an inner function _drawPanther() every frame during music. Hoisted to module scope to eliminate the per-frame closure allocation
  • Per-frame array allocations eliminated: _templeTorchSlots and _discoPitfire.gorillaScreen were created as new arrays [] every frame. Now pre-allocated and reused with .length=0
  • Temple/primate dancing event fixed: drawTempleMonkeys() and drawTempleMorphGlow() previously triggered for ALL music. v5.3.9 - Hard-Gated Retro Detection: Disco Ball Fixed for Real
2026-08-10
  • Root cause identified and fixed: Previous versions (v5.3.4–v5.3.8b) used "participation scoring" in _detectRetroMusic() — every scoring factor contributed points regardless of whether the music was actually retro. This meant ALL music (pop, rock, EDM, ambient, classical) scored 0.4–0.6, above every threshold tried. No matter how high the thresholds were raised (0.50, 0.55, 0.62), typical music still passed because the scoring function itself was fundamentally broken — it rewarded "moderate" characteristics that describe almost all music
  • Hard gates replace participation scoring: _detectRetroMusic() now uses three hard gates that return 0 immediately when key retro characteristics are absent:
    • Gate 1 — Mid-frequency dominance: midRatio < 0.43 → return 0. 80s synth/city pop has synth leads + vocals concentrated in mids (midRatio 0.44–0.55). Modern pop/rock/EDM has midRatio 0.30–0.42. This is THE key discriminator
    • Gate 2 — Moderate energy: energy < 0.06 || energy > 0.24 → return 0. Modern EDM/rock is too loud; ambient is too quiet. Retro lives in 0.06–0.24
    • Gate 3 — Moderate bass: bassRatio > 0.34 → return 0. Modern bass-heavy music (EDM, hip-hop) has dominant bass. Retro synth bass is melodic, not dominant
    Only music passing ALL three gates can accumulate a non-zero score. Pop/rock/EDM/ambient = score 0 = _isRetro stays false = moon travels normally
  • Thresholds adjusted for hard-gated scoring: Per-frame threshold lowered to 0.50 (was 0.55) because non-retro music now returns exactly 0 — any score > 0 means gates passed. retCount > 42/60 (70%, was 48/60 = 80%). avgRet > 0.50 (was 0.62). These thresholds are now meaningful because the scoring function actually discriminates
  • Disco ball trigger further reduced: Trigger chance lowered to 8% (was 10%), retry cooldown raised to 50s / 3000 frames (was 40s / 2400 frames), active duration reduced to 8-15s / 480-900 frames (was 10-20s). The moon travels the night sky normally for ALL non-retro/non-citypop music
  • CityPop path verified safe: The _isCityPop path for the disco ball requires P._isCityPop && P._cityPopJungle — _cityPopJungle is only set when the USER explicitly opts into jungle theme via the CityPop mode selection overlay. This path is correctly user-gated and does not auto-trigger

Performance Guidelines

  • Cache gradients with cache keys to avoid recreating every frame
  • Use fillRect over arc where possible (rectangles are faster)
  • Limit particle counts and use early-exit conditions
  • Music-reactive values use _smoothEnergy with lerp for smooth transitions
  • Avoid creating objects inside the render loop

Color System

All colors use hsl(h,s,l) and hsla(h,s,l,a) helper functions. Night-aware rendering checks nf (nightFactor):

ctx.fillStyle=nf>0.5 ? hsl(220,8,22) : hsl(220,12,55);

Audio Response

The analyzer splits frequency data into 8 bands. Each building is assigned a band via (i + layer*7) % 8. The _smoothEnergy property on each building lerps toward the band energy for smooth animation:

var bandIdx=((i+li*7)&7);
var bandEnergy=bands[bandIdx];
b._smoothEnergy+=(bandEnergy-b._smoothEnergy)*0.35;
dynH=b.h*clamp(0.3+b._smoothEnergy*2.2, 0.3, 2.5);
